RELEASE 2.9.5

2.8 → 2.9 新增了什么

四项改动都指向同一个目标：把「更新怎么到位」「题目从哪来」「工具从哪装」这些原本靠人工补位的环节收进工作台内部。以下描述均以当前测试版的实际行为为准。

01应用内在线更新

入口在 设置 → 关于 → 在线更新。启动 20 秒后自动首查，此后每 6 小时检查一次，也可随时手动检查。

  • 更新清单以 Ed25519 签名，客户端内置公钥验签；验签失败一律拒绝更新，不会退化为信任未签名清单
  • 安装包按清单声明的 SHA256 与字节数逐一校验，不匹配即删除，不留半成品
  • 替换由独立更新进程执行：关停 daemon、备份、替换、重启，任一文件写入失败即整体回滚并保留现场快照
  • 下载过程显示进度、速度与剩余时间；更新期间要求没有运行中的任务

02平台题目接入

AI 题目管家按平台形态选择建题链路，并明确「谁负责启动靶机环境」，避免任务内 Agent 反复调用只读工具耗尽上下文。

  • 平台提供 HTTP Open API：建题时由工作台启动容器，并把访问地址写进题面
  • 平台只提供 MCP 工具：管家在建题前调用启动工具并轮询到地址
  • 平台容器配额满额时登记待补题，按 45 秒间隔重试最多 8 次，不再出现「第 N 题起静默不补题」
  • 任务侧不投递破坏性工具，提交 Flag 等能力走独立通道

03统一对话栏双模式导入

对话式建题与比赛 API 批量导入合并到同一条入口，由意图路由决定走哪条路径，单题与批量不再分散在两处。

  • 单题模式按对话补充题面、授权目标、Flag 格式与附件
  • 接入比赛 API 后可批量导入题目，按本机调度容量逐题启动
  • 附件走安全落盘与去重，不把远端内容直接当成本地路径
  • Flag 提交仍以人工确认为前提，不自动替操作者做授权判断

04工具链扩展成三条通道

Windows 基础工具、WSL 基础工具与受管 Python 依赖彼此独立，各自拥有不同的执行位置与授权方式。

  • WSL 基础工具在所选发行版内以独立隔离环境运行，普通任务与 Worker 按需调用
  • 受管 Python 依赖在隔离目录构建固定版本 wheel，完全重启后原子发布，失败可回退
  • 发布模板附带 25 项 Windows 与 19 项 WSL 示例条目，可用 AI 辅助扫描本机工具目录生成配置
  • 基础工具检测不会下载、安装或更新任何程序

START TO SOLVE

从解压到 Writeup，一条完整路径

工作流围绕授权边界、可见过程和人工判断设计。第一次使用先完成沙箱、许可证、模型和基础工具准备。

启动流程

完整解压，不要只复制主程序

  1. 01解压发布包

    放到当前用户可写、路径较短的目录，保持所有 EXE、defaults/ 与运行文件结构不变。

  2. 02启动工作台

    运行 CTF-BTFly.exe；首次 Broker 准备可能出现一次 UAC 请求。

  3. 03等待沙箱 Ready

    在“Windows 沙箱”查看 preparing / ready / unavailable 和具体诊断。

  4. 04配置模型与工具

    导入许可证，检测至少一个模型；按需选择基础工具、Tool Pack 和 MCP。

做题流程

候选结果必须经过人的确认

  1. 01创建题目

    填写题面、授权范围、目标、Flag 格式，添加附件并选择网络范围。

  2. 02选择模式

    快速主线用标准模式；需要分工用黑板；复杂路线用超级模式。

  3. 03观察与干预

    在过程、终端、文件与黑板中查看证据；可暂停、补充线索、切换模型或重试。

  4. 04审核并交付

    人工确认 Flag 或答案后，生成中文 WRITEUP.md 和关键 Artifact。

TOOLS & EXTENSIONS

工具可扩展，边界不打折

Windows 基础工具、WSL 基础工具、受管 Python 依赖、Tool Pack 与 MCP 是五条独立能力通道。任务只获得启动时冻结并授权的能力集合。

01

Windows 基础工具

通过用户选择的 Windows 目录与 JSON 动态检测；在 AppContainer 中只读、可执行。

02

WSL 基础工具

选择发行版、Linux 目录与 JSON，在发行版内的隔离环境中按需调用；应用不安装软件、不初始化 WSL。

03

受管 Python 依赖

声明精确版本后隔离构建 wheel，重启时原子发布；构建失败可回退到发行默认。

04

Tool Pack

绑定精确的 id / version / digest，校验和授权成功后才对后续任务可见。

05

MCP Server

经 daemon 网关按任务令牌、题型与策略过滤，并记录工具调用审计。

WINDOWS NATIVE SANDBOX

不是把命令藏起来，
而是把执行边界做清楚

daemon 负责本地控制平面，Broker 负责受控提权与权限准备，Runner 在每题独立 AppContainer Profile 中启动受信 Pi。

01

每题独立身份与进程树

Profile SID、工作区、控制目录、命名管道与 Job Object 随任务创建。

02

工具只读挂载

共享运行时与基础工具仅授予读取/执行；Tool Pack 权限绑定精确内容摘要。

03

短期任务令牌

模型与 MCP 访问经过 daemon relay，令牌绑定任务并限制调用范围。

04

失败保留现场

无法证明一致性的在途状态进入暂停或 recovery_required，不会静默标记完成。
